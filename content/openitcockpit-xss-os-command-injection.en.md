# 7. openITCOCKPIT XSS and OS Command Injection - black box testing

[openITCOCKPIT](https://openitcockpit.io/) is an application designed to assist in the configuration and management of two common monitoring tools - [Nagios](https://www.nagios.org/) and [Naemon](https://www.naemon.org/). The vendor offers both an open source community version and an enterprise version with advanced extensions.

Although openITCOCKPIT Community Edition is open source software, this module initially uses a black-box approach to exploit a Cross-Site Scripting vulnerability. The complete exploit chain will ultimately enable Remote Code Execution (RCE).

The vulnerabilities were discovered by Offensive Security and are now numbered CVE-2020-10788, CVE-2020-10789, and [CVE-2020-10790](https://openitcockpit.io/security/#security).

# 7.2. Black box testing of openITCOCKPIT

Even though openITCOCKPIT is an open source application, we try to find vulnerabilities without looking at the source code to simulate black box testing. We do not have access to source code, architecture diagrams, or debugging environments, so test coverage is limited.

Therefore, time must be allocated wisely to check as many applications as possible. As we gain experience, we learn to judge when to continue investigating a feature and when to move on to other goals, and gradually develop a keen intuition for identifying unusual errors and behaviors.

For example, a "SQL syntax" error obviously implies a possible SQL Injection. When performing a white-box evaluation, we inspect the code; if the input is not properly escaped, we can construct exploit code. But in a black-box evaluation, we might not be able to find the correct string that triggered the injection, or the input might have been escaped correctly and the error was caused by something else. If you focus all your resources on one potential vulnerability, you may miss other attack vectors.

The process of this module has a certain cyclic nature. In order to discover information that can be used to further exploit an application, multiple threads need to be correlated.

The discovery phase of this module and building an accurate sitemap are both crucial. The first step is to build a sitemap to gain a holistic understanding of the endpoints your application exposes and the libraries it uses.

# 7.3. Application discovery

To discover exposed endpoints, first visit the application home page and observe what other endpoints the application requests when generating the page.

Directories containing images, CSS, and JavaScript may seem negligible, but they may contain clues about how your application works. In a black box assessment, every clue may have value.

# 7.4. Introduction to DOM-based XSS

To understand DOM-based XSS, you must first become familiar with the Document Object Model ([DOM](https://developer.mozilla.org/en-US/docs/Web/API/Document_Object_Model/Introduction)). When a browser interprets an HTML page, it renders individual HTML elements and creates objects for each element for display. For example, *div* can contain *h1*; when parsed by the browser, a *div* object is created with the *h1* object as a child node. A hierarchical [tree](https://developer.mozilla.org/en-US/docs/Web/API/Document_Object_Model) composed of objects representing each HTML element is the Document Object Model. HTML elements can be passed [id](https://developer.mozilla.org/en-US/docs/Web/HTML/Global_attributes/id), [class](https://developer.mozilla.org/en-US/doc s/Web/HTML/Global_attributes/class), tag [name](https://developer.mozilla.org/en-US/docs/Web/API/Element/tagName) and other identifiers, these identifiers will be passed to Objects in the DOM.

The browser generates the DOM from the HTML so that the page can be manipulated programmatically via JavaScript. Developers can use JavaScript in the client browser to manipulate the DOM, perform background tasks, UI changes, and more. Although it is also possible to dynamically generate HTML on the server side and send it back to the user to complete these changes, this will introduce significant latency to the application.

To achieve this kind of operation, JavaScript provides the [Document](https://developer.mozilla.org/en-US/docs/Web/API/Document) interface. When querying objects in the DOM, the *document* interface provides APIs such as *getElementById*, *getElementsByClassName*, and *getElementsByTagName*. The object returned by the query inherits from the *Element* base class; the *Element* class contains properties such as *innerHTML*, which are used to manipulate the content within HTML elements. The *Document* interface can also write directly to the DOM through the *write()* method.

*DOM-based XSS* can occur if unsanitized user input is provided to attributes such as *innerHTML* or methods such as *write()*.

For example, consider the inline JavaScript in Listing 9.

```html
<!DOCTYPE html>
<html>
<head>
  <script>
    const queryString = location.search;
    const urlParams = new URLSearchParams(queryString);
    const name = urlParams.get('name')
    document.write('<h1>Hello, ' + name + '!</h1>');
  </script>
</head>
</html>
```
- DOM XSS example

In Listing 9, the JavaScript between the script tags first extracts the query string from the URL. The constructor of the [URLSearchParams](https://developer.mozilla.org/en-US/docs/Web/API/URLSearchParams) interface parses the query string and returns a *URLSearchParams* object, which is saved to the *urlParams* variable. Then use the *get* method to extract the name from the URL parameter; finally use the name passed in the query string to write the *h1* element into the document.

Save the HTML content of Listing 9 to `/home/kali/xsstest.html`. This demonstration does not require Apache; executing `firefox xsstest.html` will open the file in a new window.

# 7.6. Advanced XSS Exploitation

After completing the exercise, we should have a basic working XSS, but the pop-up alert is far from a true "exploitation". Next, you need to design strategies to improve current access capabilities, but the information available to construct targeted XSS attacks is very limited.

## 7.6.1. What you can and cannot do

Reflected DOM-based XSS offers limited exploitation opportunities. The following analyzes the operations that can and cannot be completed currently.

First, a victim is needed. Stored XSS can attack anyone who visits the page, and a specific link must be made and sent to the victim; XSS will be triggered only after the victim visits.

If you use Burp to examine the requests and responses sent and received by your application, you may notice a cookie named *itnovum*. - Check HttpOnly

Although the user session cookie cannot be read, we can access the DOM and control what the web page loads and renders via XSS. When the browser requests content from the page, whether triggered by a refresh or JavaScript, the session cookie is automatically carried, even if JavaScript cannot directly access the cookie value. Therefore, it is possible to add content to the authenticated victim's DOM via XSS, loading resources that are only accessible to the authenticated user. JavaScript can manipulate the DOM, but browsers restrict its access through the *Same-Origin Policy* ([SOP](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy)).

SOP allows same-origin pages to communicate and share resources. For example, JavaScript running at `https://openitcockpit/js/vendor/lodash/perf/index.html` can use *XMLHttpRequest* ([XHR](https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest)) or [fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch) Sends a request to `https://openitcockpit/` and reads the response content. Because the XSS is on the target domain name, any page from the same origin can be loaded and the content retrieved. If the XSS victim is logged in, the browser will automatically send its session cookie when XHR requests content, allowing us to borrow the existing user session to access the authenticated content.

This also means that the SOP will prevent JavaScript from accessing content from different origins. For example, JavaScript running on **https://evil.com** can send an XHR request to **https://google.com**, but the SOP will prevent it from reading the response.

This information can be used to crawl the homepage via XSS to the authenticated victim. Once the page loads, find all the links, load them with XHR, and forward the content back to get the authenticated user's data and potentially open new exploit paths.

XSS will only run if the victim keeps the relevant window open. While there are some tricks to slow down the victim's window exit, XSS should still be executed as quickly as possible.

Although it is possible to take advantage of some features of *The Browser Exploitation Framework* ([BeEF](https://beefproject.com/)), BeEF is not used here because achieving the goal requires a lot of effort to develop a new plugin and configure BeEF. We will write our own application, which consists of three main components: the XSS payload script, a [SQLite](https://www.sqlite.org/index.html) database to save the harvested content, and a [Flask](https://palletsprojects.com/p/flask/) API server to receive the XSS payload harvested content. A database is not strictly necessary, but it makes it easier to extend the application to complete some of the advanced exercises.

In addition to the three main components, the following conditions must be met:

1. The XSS page must be realistic enough to prevent the victim from leaving.
2. The content captured and stored in the database is used to reconstruct the remote HTML file locally; create another script to export the database content.
3. Database scripts must be able to be imported and called by multiple scripts to save time and reuse code.

[WebSocket](https://en.wikipedia.org/wiki/WebSocket) is a communication protocol supported by browsers. The initial connection uses HTTP, and then a full-duplex connection is established so that the client and server can communicate quickly. HTTP is a stateless protocol, while WebSocket is stateful. In a correct implementation, the initial HTTP connection authenticates the user, and subsequent WebSocket requests do not require re-authentication. However, due to the complexity of WebSocket programming, developers often implement authentication by themselves. In openITCOCKPIT, the same object containing *websocket_url* also provides the key, presumably for authentication.

WebSocket communication is often overlooked in penetration testing. Until recent versions, Burp Repeater did not support WebSocket messages, and Burp Intruder still does not. But WebSocket may have as much control over the server as HTTP. A WebSocket endpoint (and key in this case) was found to significantly increase the risk level of the application.

WebSocket connections in browser applications are initiated by JavaScript. JavaScript is not compiled, so the source code that defines the connection must exist in some JavaScript file when the page loads. You can use this to learn how to communicate with a WebSocket server and create your own client.

## 7.7.5. Try to inject commands

At this point you should have discovered that *ls* is a valid command. Let's try to use common injection techniques to escape the command.

One method of command injection is to "stack" commands using operators such as *&&*, *||*, etc. When the previous command succeeds *&&* executes the next one; when the previous command fails *||* executes the next one. While there are other injection techniques, instead of manually testing each one, you can use a compiled list to blast through every possibility.

For example, the attack dictionary [Fuzzdb](https://github.com/fuzzdb-project/fuzzdb) for black-box testing contains a list of potential injections and can be downloaded directly from GitHub.

```console
kali@kali:~/scripts$ wget -q https://raw.githubusercontent.com/fuzzdb-project/fuzzdb/master/attack/os-cmd-execution/command-injection-template.txt

kali@kali:~/scripts$ cat command-injection-template.txt 
{cmd}
;{cmd}
;{cmd};
^{cmd}
...
&CMD=$"{cmd}";$CMD
&&CMD=$"{cmd}";$CMD
%0DCMD=$"{cmd}";$CMD
FAIL||CMD=$"{cmd}";$CMD
<!--#exec cmd="{cmd}"-->
;system('{cmd}')
```
- Download FuzzDB command list

This list uses a template where *{cmd}* variables can be replaced. Traverse each injected template, send it to the server and check the response to determine whether there is technology that can inject the template.

### practise

1. What error message is displayed when submitting characters that are not allowed?
2. Modify the fuzzing script to use `command-injection-template.txt`. Replace `{cmd}` placeholder with the command to be executed (such as `whoami`) and check the output to determine whether the injection technique is successful.

Pause and analyze possible internal implementations. The WebSocket connection receives input that is expected to be executed, but the developer does not want the user to run arbitrary commands, so only certain commands are added to the allowlist, including `ls` and commands in the current directory. The output after appending "--help" also shows that they want to execute the command as a specific user, so *su* is used. It can be speculated that the actual command is similar to the following:

- speculative command

Since single quotes can escape the command that the developer expects to execute, it is reasonable to speculate that user data is wrapped in single quotes. It is also speculated that this data is passed to `su`'s `-c` (short for command) flag and executed under the username provided to `su`. After appending single quotes, you can escape the original package and inject it directly into the `su` command.

Since it is suspected that the developer passed `-c` into the target command, what will happen if another `-c` is passed in?
